# maisecrets: Windows and Linux threat review (persistent pointers)

Scope: `/Users/akruse/maisecrets`, read on 2026-09-26. Tags: **VERIFIED** = a cited doc or the repo code says it; **ASSUMED** = my judgement, not checked.

## 1. Windows: PasswordVault (Credential Locker)

- **Who can read.** `WindowsVaultBackend.get` starts a new `powershell -Command` with no package identity and reads any entry by resource and user name (`maisecrets/vault.py`, class `WindowsVaultBackend`). So every unpackaged process in the user session can do the same. **VERIFIED by code.** Microsoft says that the Locker "cannot be locked", that "users cannot be prompted to consent" to a release, and that nothing changes for "legacy Windows applications" ([Credential Locker overview, archived](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-8.1-and-8/jj554668(v=ws.11))). **VERIFIED.** Isolation by package identity applies only to packaged apps. **ASSUMED.**
- **Roaming.** "Credential roaming is enabled by default on non-domain-joined computers"; on domain-joined computers it is off, and new credentials that you add under a domain account do not roam (same source, plus the [current doc](https://learn.microsoft.com/en-us/windows/apps/develop/security/credential-locker)). **VERIFIED.** `PasswordCredential` has no per-entry "do not sync" flag. **ASSUMED.** A user or admin can stop password sync in Settings > Accounts > Windows backup, or by policy (secondary sources only: [NinjaOne](https://www.ninjaone.com/blog/disable-sync-of-apps-and-preferences/)). **ASSUMED.** The plugin cannot opt out for one entry. The README line "no sync" applies to the macOS keychain only.
- **Capacity.** "You can only store up to 20 credentials per app" (current doc). **VERIFIED.** It is not known if Windows enforces this limit for an unpackaged caller. **ASSUMED.** With a 24 h TTL and PII detection, more than 20 live entries is realistic.
- **Better fit.** `CredWrite` with `CRED_TYPE_GENERIC` and `CRED_PERSIST_LOCAL_MACHINE` is "not visible to logon sessions for this user on other computers", and the blob limit is 2560 bytes ([CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)). **VERIFIED.** A DPAPI blob (`CryptProtectData`, no `CRYPTPROTECT_LOCAL_MACHINE`) can be decrypted only by the same user on the same computer, with a roaming-profile exception. It includes a MAC, and `CRYPTPROTECT_AUDIT` writes an audit record ([CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)). **VERIFIED.** Both options stop the cloud roaming. Neither option stops a same-user process. Optional DPAPI entropy adds nothing if the entropy is stored where the user can read it. **ASSUMED.**

## 2. Linux: encrypted file

- **What it protects.** It protects a copy of `vault.enc.json` that leaves the machine without `~/.maisecrets/key`, for example a partial backup or an accidental attach. **VERIFIED by code:** key and data are in the same directory, both 0600. It does **not** protect against a same-user process, root, or a full home backup. Mode 0600 alone gives the same protection against other local users.
- **`MAISECRETS_KEY_FILE` "root-managed".** `openssl` runs as the user and reads the key with `-pass file:`. So the key must be readable by the user, and "root-managed" does not add isolation. **VERIFIED by code.**
- **PBKDF2 at 100k iterations.** The input is a random 32-byte key. Iterations "increase the time required to brute-force" a password ([openssl-enc](https://docs.openssl.org/3.0/man1/openssl-enc/)). **VERIFIED.** A 256-bit random key cannot be brute-forced, so the iterations are theatre that costs latency on every hook call. The salt gives a new key and IV per value, which is useful. `openssl enc` "does not support authenticated encryption" (same source), so the separate HMAC is necessary. **VERIFIED.** The tag does not bind the entry name, so a user who can write the file can swap two ciphertexts. **VERIFIED by code**, low impact.
- **Secret Service / GNOME Keyring / KWallet.** The spec "does not mandate any form of access control" ([Secret Service spec, ch. 10](https://specifications.freedesktop.org/secret-service/latest/ch10.html)). **VERIFIED.** When the collection is unlocked, any same-user application can read every secret (CVE-2018-19358, [ArchWiki](https://wiki.archlinux.org/title/GNOME/Keyring)). **VERIFIED (secondary source).** So on a desktop it gives the same same-user exposure as the file. Its advantage is that the key is derived from the login password and not stored on disk. On a headless server no session bus and no unlocked collection exist, so the file or the kernel keyring is the practical choice. **ASSUMED.**
- **Kernel keyring.** Keys live in kernel memory and do not survive a reboot. A persistent keyring expires after 3 days without access ([keyrings(7)](https://man7.org/linux/man-pages/man7/keyrings.7.html)). **VERIFIED.** This is a good store for the pointer HMAC key on a server, because no key file exists at rest.

## 3. Rate limits and audit in the OS stores

No store limits the read rate. PasswordVault and CredRead document none. **ASSUMED.** The Secret Service mandates no access control. **VERIFIED.** A file has no limit. Audit: Windows event 5379 "Credential Manager credentials were read" exists ([UltimateWindowsSecurity](https://www.ultimatewindowssecurity.com/securitylog/encyclopedia/event.aspx?eventid=5379)). Microsoft's subcategory list shows only 5376/5377 ([Audit User Account Management](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/audit-user-account-management)), so default coverage is **ASSUMED**. On Linux, `auditctl -w <path> -p r` records opens of the key or vault ([auditctl(8)](https://man7.org/linux/man-pages/man8/auditctl.8.html)). **VERIFIED.** Conclusion: the plugin must supply its own limiter and log.

## 4. Pointer model versus stored values

- **Capability does not change.** An agent with Bash can already read `.env`. Pointers do not grant new access to the value. They add a stable handle that expands in any command in any session. The ease of exfiltration increases, and the time window grows from 24 h to unlimited. **ASSUMED.**
- **Integrity is the new risk.** Rehydration reads the source at execution time. Anyone who can write that file then controls the text that `pre_tool` splices **unquoted** into a shell command (`resolved = resolved[:start] + value + resolved[end:]`, `maisecrets/hooks.py`, `pre_tool`). **VERIFIED by code.** On a network share or in a synced folder (OneDrive, Dropbox, a git pull), this group includes colleagues, the sync provider account, and a compromised device. The same unquoted splice already applies today to values that `post_tool` vaults from untrusted tool output.
- **Network share.** The value crosses the network on every use, and the source can be absent. **ASSUMED.**
- **Fingerprints.** A keyed HMAC is better than the current `index.json` fingerprint, which is `sha256(value)[:12]` without a key (`vault.py`, `fingerprint`). That fingerprint lets a reader of the index confirm guesses of low-entropy PII such as a phone number or a tax ID. **VERIFIED by code.** Whitespace tokenization misses a value inside quotes, in `KEY=value`, in JSON or in a URL, so redaction gaps remain. **ASSUMED.**

## 5. "Ask before rehydrate"

- **What it defends.** It stops a placeholder-based exfiltration command that a human reads and rejects.
- **What it does not defend.**
  - If the hook returns `updatedInput`, the prompt probably shows the resolved plaintext on screen. **ASSUMED.** The docs do not describe how `ask` and `updatedInput` combine ([hooks](https://code.claude.com/docs/en/hooks)).
  - Hook stdout goes "to the debug log" (same source). **VERIFIED.** That stdout contains the resolved command.
  - The control does not see commands that read the source file directly, print the environment, or copy `~/.maisecrets` or the key file. None of these carries a placeholder.
  - Repeated prompts cause approval fatigue.
- **Controls that close the gaps.**
  - Enable the Claude Code sandbox with `credentials.files` `deny` on every registered source, on `~/.maisecrets` and on the key file, plus a network allowlist. The plugin can write these entries at `protect` time.
  - Use `mask` with `injectHosts`: the command sees a sentinel, and the proxy puts the real value only on requests to allowed hosts ([sandboxing](https://code.claude.com/docs/en/sandboxing)). **VERIFIED.** This is the destination-bound design that persistent pointers need.
  - Limitation: the sandbox runs on macOS, Linux and WSL2, and "Native Windows is not supported" (same source). **VERIFIED.** On native Windows, only the hook and a human remain.

## 6. Recommendations (ranked)

1. **Shell-quote or reject on rehydration (S).** Quote each value for bash, or deny values with shell metacharacters. Defends against command injection from a tampered source file or from untrusted tool output.
2. **Integrity pin for pointers (S).** At rehydration, compute the HMAC of the value that you read and compare it with the registered fingerprint. If they differ, deny and require a new `protect`. Refuse sources on network or sync paths. Defends against tampering on a share or in a sync folder, and against TOCTOU.
3. **Put pointers behind the sandbox (M).** Write `credentials` deny entries for the sources and the vault, and prefer `mask` + `injectHosts` for each pointer. Defends against direct reads, environment dumps, vault copies, and egress to unknown hosts (not native Windows).
4. **Plugin limiter and audit log (M).** Allow at most N distinct refs per session per hour. Use `ask` on the first use of a persistent ref in a session. Show the placeholder form in `permissionDecisionReason`. Write an append-only log of key, session, command hash and time. Defends against bulk automatic outflow; the OS stores give no limiter.
5. **Windows: move from PasswordVault to `CredWrite` `CRED_PERSIST_LOCAL_MACHINE` or a DPAPI file (M).** Defends against roaming to other devices through the Microsoft account and against the 20-entry limit.
6. **Key the index fingerprint (S).** Replace `sha256(value)[:12]` with an HMAC under a vault key. Defends against offline guessing of low-entropy PII from `index.json`.
7. **Linux: pointer key in the kernel keyring or the Secret Service where present; drop PBKDF2 iterations (S).** Defends against key-at-rest in backups. Removes latency that has no security value.
8. **Document the real boundary (S).** State in the README: "Any process of the same user can read every store." Defends against a false sense of isolation.
