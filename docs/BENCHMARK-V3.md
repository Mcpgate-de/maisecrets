# Benchmark V3

Status: the method is fixed and executable (2026-10-21); `docs/BENCHMARK-V3-DRAFT.md` holds the evidence that led to
it (the false-positive audit and the prose-miss audit). V1 and V2 stay as they are: no V1 or V2 number is scored again
or overwritten, and a V3 report names its own run.

## What V3 measures, and why it changes

V3 asks how well maisecrets generalises: how it does on data that no rule was written from. Three faults of V1 and V2
made that unclear.

1. **The comparison samples were `dev` alone.** V1 and V2 compared the scanners on a fixed sample, "1 in 50 by the
   sha256 of the case id". The split rule takes the same hash modulo 10 (0–5 `dev`, 6–7 `val`, 8–9 `holdout`). A
   number divisible by 50 is divisible by 10, so every sampled case was `dev`: the split whose cases were read to
   write the rules of 0.6.40 to 0.7.3. Counted on 20,000 ids: 0 of the sampled ids outside `dev`
   (`tests/test_bench.py`, `BenchmarkV3Tests`). Every cross-scanner table of V1 and V2 compared maisecrets on its own
   development data. V3 salts the sample (`--sample-salt v3/`), which spreads it over all splits.
2. **A false positive in a class the dataset never labels counted as wrong.** An e-mail address in Privy, whose test
   split has no e-mail label, lowered maisecrets' precision there. V3 counts a false positive only in a class the
   dataset labels; the rest is reported apart as out of scope (`bench/v3.py`).
3. **Labels that are not exhaustive.** A read sample (the draft, "The audit result") showed that most of Nemotron's
   SSN and Gretel's bank-account false positives are real values without a label. V3 reports their precision as a
   lower bound.

## The scoring

- **Recall** is unchanged: a span counts when it is masked whole (strict), partly (lenient), or not at all.
- **Scope** per dataset (`bench/v3_scope.json`, generated by `python3 bench/v3.py --inventory` from the label mapping
  of `scripts/measure_datasets.py`, compared by a test): the classes the dataset's labels map to. Privy: names,
  national ids (driver licenses, passports, ITINs), cards, bank accounts, passwords; its IBANs are out (reached only
  by retyping a bank label) and so is an SSN shape inside national ids (Privy labels no SSN), also inside a wider
  finding such as `SSN: …` (since codex Gate A; on 2026-10-22 it changed no number of the Privy runs of maisecrets,
  Presidio, Preserve and pii-anon). The bank, the traces,
  the catalogs and the holdout are written by this project and label every class they use.
- **Precision (V3)** = findings on a labelled span / (those + false positives in scope). A secret finding counts in a
  dataset that labels any secret. The `v3` block of each result file holds the false positives in scope, the ones out
  of scope per class, and the lower-bound classes.
- **The same for every scanner.** The scope is a property of the dataset, never of a scanner; a scanner is still
  scored only on the classes it claims (its adapter's `SCOPE`).

## Secret datasets (added 2026-10-22)

Three public sets with labelled secrets. Each one is pinned in `scripts/measure_datasets.py` (`SOURCES`), and
`python3 scripts/measure_datasets.py fetch --only aparte,llmredactor,credsweeper` writes it into the data directory.
The fetch of LLM-Redactor needs pyarrow. Their values are fake or test values by their cards. Run them with
`bench/run.py --source <name> --split dev|val|holdout`. `bench/run_all_v3.sh` does not run them yet.

### aparte (`apartejs/aparte-secrets-gold`)

Real chat messages from WildChat (English and French) with fake secrets that an LLM put in, and code snippets and
framework configs. Licence ODC-BY 1.0. Revision `efca9c0004ac8435ef58c0dcaec61c88605fbb76`. The spans are the card's
`secrets` (code-point offsets). The `decoys` (UUIDs, SHAs, IBANs, example and masked keys) are no spans, so a finding
on one is a false positive. The config `gold` (775 texts) is development data, because the makers of a competing
detector tuned on it. The split rule divides it into `dev` (465) and `val` (310); its holdout part goes to `val`. The
configs `chat-fresh` and `chat-fresh-json` (440 texts each, the same messages as JSON) are the `holdout` split (880).
Classes: `password` → `secret.password`, `api_key` and `token` → `secret.token`, `private_key` →
`secret.private_key`, a secret without a subtype → `secret.generic`. Channel `prompt`. The context comes from the
mode: chat → prose, `chat_json` → json, tech → code, framework → config. It labels no PII.

### llmredactor (`jayluxferro/llm-redactor-leak-benchmark`, workload `wl2_secrets`)

300 synthetic prompts to an LLM (configs, code, shell commands, logs). Licence MIT. Revision
`113f7676dbf5f8ec0152c3f3bd87150cc81f4662`. Split by the split rule: `dev` 187, `val` 52, `holdout` 61.
Classes: `password` → `secret.password`; `api_key`, `bearer_token`, `aws_access_key` → `secret.token`;
`aws_secret_key` → `secret.generic`; `pem_private_key` → `secret.private_key`; `email` → `pii.email` and `ip_address`
→ `pii.ip` (with the existing label cleaning: a reserved domain or a private address is neutral); `hostname` is
neutral. Channel `prompt`. The context is a guess from the first lines (`context_of`).

### credsweeper (`Samsung/CredSweeper`, `tests/samples`)

The test samples of CredSweeper, one case per text file (199 files; 47 binary files are left out). Licence MIT.
Commit `b4875caf368bbc08d4d9431b714ad114608edf2c`. The archive of GitHub is not byte-stable, so the pin is the
sha256 over the extracted files (`tree_sha256`). The spans come from CredSweeper's expected output of its default run
(`tests/data/output.json`, line number and value offsets per line). Its rules give the class: a password rule →
`secret.password`, a private key → `secret.private_key` (one span per key), a keyword rule (`Token`, `Key`, `Secret`,
…) → `secret.generic`, a provider rule → `secret.token`. Neutral: info and low severity rules (UUID, bucket names,
salts), each value in a negative sample (`*_n`, `*_fp`, `false_positive`), and the values that only its other runs
report (`no_ml.json`, `doc.json`). The rest of a file is negative text. Split by the split rule on the file name:
`dev` 114, `val` 35, `holdout` 50. Channel `tool`, the path is the file name, the context comes from the extension.
The labels are the output of one scanner, so its precision is probably a lower bound; no read sample checks it yet.

## The result schema

Each result file of `bench/run.py`: `scanner` (name, version, commit, configuration, installed distributions),
`bench_commit`, `bench_dirty`, `source`, `split`, `every`, `sample_salt`, `cases`, `cases_sha256`, `source_meta`
(dataset revision and licence), `metrics` (V1/V2: per class and family `spans`, `full`, `partial`, `missed`,
`recall_strict`, `recall_lenient`, `fp`, `precision`, `f1`), `by_region`, `by_context`, `timing`, `per_case` (the
outcome of each span and one `fp` per false positive, per case id) and `v3` (per family `on_target`, `fp`,
`out_of_scope` per class, `precision`; the dataset's `scope` and `lower_bound`).

## Holdout V2 on a release candidate

The procedure is `bench/holdout_v2.py` (docs/BENCHMARK-V2.md, "Holdout V2"). On a release candidate:

1. The template author has not seen a maisecrets miss list (`ATTESTATION.json`); the templates cite the public specs of
   `bench/holdout_v2_specs.json` and stay private.
2. `check`, `generate` and `seal` once; the manifest `bench/holdout-v2.manifest` is committed before the first run.
3. `bench/run.py --scanner maisecrets --maisecrets <RC checkout> --source holdout-v2 --holdout <private cases>
   --release-candidate` refuses without the seal, on a changed file, or when the checkout is not a clean tip of
   `next` or `main` or a `v` tag; it writes one row to `bench/HOLDOUT-LOG.md`, totals only.
4. No rule changes because of a holdout result; a holdout that was read for tuning becomes development data.

### Holdout V2 on the release 0.7.4 (2026-10-21)

The first run of the independent holdout (872 cases, written by an agent that saw no miss list; `bench/HOLDOUT-LOG.md`):

| | Spans | Recall strict | Recall lenient | Precision | False positives |
|---|---:|---:|---:|---:|---:|
| Secrets | 330 | 0.588 | 0.864 | 0.997 | 1 |
| PII | 498 | 0.651 | 0.703 | 0.995 | 2 |
| Both | 828 | 0.626 | | 0.9955 | 3 |

Its weak classes (totals of the class only): names 5 of 48 whole, connection strings and URL credentials masked in
part only (48 of 48 and 37 of 42 partial; the holdout is not read, so which part stays open), tax ids 24 of 42, user
names 18 of 36, passwords 24 of 48. Tokens and private keys are whole in all 108 spans.

**A partial connection string is the intended behaviour, not a gap** (the maintainer's decision, 2026-10-22).
maisecrets masks the credential of `postgres://user:password@host/db` and keeps the scheme, the user, the host and the
database, so the model can still work with the connection: `postgres://user:<placeholder>@host/db`. Strict recall
counts that as partial, because the gold span is the whole string. A partial span here is a difference of policy and
scoring, not a leak, as long as no sensitive part stays in plain text; maisecrets is not tuned to mask the whole
string for strict recall.

A metric for this, as a proposal and not yet part of the method: **leak-safe coverage**, the share of gold spans whose
sensitive component (the password, the token, the key, the value of a personal field) is masked, whatever the span
masks around it. It needs a second annotation per class (which part of a span is the sensitive component: the
password of a URL, all of a token), so it is noted here and not built. Lenient recall (any overlap) is an upper bound
of it today; on Holdout V2 it is 0.864 for secrets against a strict 0.588.
